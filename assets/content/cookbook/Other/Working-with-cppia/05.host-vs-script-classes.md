# Host classes versus script classes

Following the previous parts of the tutorial, we now have two programs:

- The script, compiled as a CPPIA file: `bin/script.cppia`
- The Host, compiled as an HXCPP program: `bin/Host[.exe]`

These two compilation methods each have their own advantages and disadvantages.

Cppia:

- Faster compile time
- Machine independent
- Slower runtime performance
- Unable to inject native C++ code or directly access libraries

Native hxcpp:

- Slower compile time
- Dependent on current operating system and cpu architecture
- Faster runtime performance
- Able to inject native C++ code and directly access libraries

To gain the advantages of both, we can control which classes are included in the Host. This way, code that is performance sensitive or that requires native C++ code/libraries can benefit from native HXCPP, while still giving the fast compile times and portability of CPPIA for the rest of the program.

## Utils.hx

Consider a new Utils class, which contains a performance critical function `runIntenseTask`:

```haxe
// Utils.hx
class Utils {
  public static function runIntenseTask() {
    #if cppia
    trace("Running intense task in cppia");
    #elseif cpp
    trace("Running intense task in hxcpp");
    #end
  }
}
```

Here is our updated Script class which makes use of this new method:

```haxe
// Script.hx
class Script {
  static public function main():Void {
    trace("Hello from Cppia SCRIPT");
    Utils.runIntenseTask();
  }
}
```

As before, we compile the script and run the host:

`> haxe script.hxml`

`> Host.hx:4: Hello from cppia HOST`\
`> Script.hx:4: Hello from Cppia SCRIPT`\
`> Utils.hx:5: Running intense task in cppia`

We can now see that our intense computation runs in CPPIA mode, which is not what we wanted. To fix this, we will need to recompile our Host.

## Including Utils in the Host

To include the `Utils` class in the Host, we must add it to the **host.hxml**:

```hxml
# host.hxml
-cp src
-main Host
-cpp bin
-D scriptable
Utils
```

> Warning: Enabling full dead code elimination (`--dce full`) when compiling a host may cause required classes to be removed from the output.

We can now recompile the Host using `haxe host.hxml` and it will include the `Utils` class compiled as native HXCPP code. We can confirm this by finding the `class Utils` entry in `export_classes.info`, which is generated when compiling the Host.

We should also recompile our **script.hxml** file, as the updated `export_classes.info` file will tell Haxe that `Utils` is included in the Host and shouldn't be compiled into the CPPIA script.

> Note: When compiling the host, we can use `-D dll_export=` flag to control the file name of the generated file specifying Host classes. During script compilation, we can use `-D dll_import=` to specify the file to read from, which is necessary if it is not in the class path.

If we now rerun the Host, we will see that `Utils.runIntenseTask` is executed in native HXCPP as we desired:

`> Host.hx:4: Hello from cppia HOST`\
`> Script.hx:4: Hello from Cppia SCRIPT`\
`> Utils.hx:7: Running intense task in hxcpp`

## Adding further classes

As we add more classes to our host build, it may become impractical to list each class individually in **host.hxml**. We may include all classes found within a package at once using the [`include` compiler configuration macro](https://haxe.org/manual/compiler-usage.html#global-compiler-configuration-macros). For example, if we wanted to include all classes in the `pack` package:

```hxml
# host.hxml
-cp src
-main Host
-cpp bin
-D scriptable
--macro include("pack")
```
